# OpenCode 2 config coverage audit

This is the recorded baseline audit, not a claim that every setting was functional in upstream 5.0.0 or that every gap is a new regression. See [the current compatibility table](opencode2-compatibility.md) for changes made after this snapshot. In particular, commit `360835f85` fixed the task schema conversion issue described below and verified all four task tools in OpenCode 2.0.18. Commit `564beb202` subsequently restored per-load MCP environment allowlists, with a real local MCP roundtrip on OpenCode 2.0.18. Commit `4925c0e39` subsequently enforced disabled providers through OMO model selection and native request guards; its local-only host QA is recorded in the compatibility document. Rows below retain the original baseline findings. The old Ralph controller consumes an iteration cap, but no current V1 goal-controller consumer was established; the unused V2 goal cap is a configuration limitation, not a proven V1-to-V2 regression.

**Baseline:** `58ba6a150ed314fbeb2d53db52ab5304fc8baa5c` (`2026-09-27`). This is a source audit of the checked-in baseline, not the later safety/task fixes. All paths/lines below refer to that baseline. Unless prefixed `packages/`, paths are relative to `packages/omo-opencode/`. `setupV2` is the default plugin setup; it loads the validated config and installs only the native registry, tool, hook, and command adapters (`packages/omo-opencode/src/index.ts:6-15`, `src/v2/setup.ts:21-34`, `src/v2/config.ts:9-26`).

Later source changes: `1a78d25c5` adds background concurrency/depth/descendant admission and resume-generation protection; `9b281ad81` adds bounded first-generation restart reconciliation, and `14ebcca63` adds persistent hard-call and repeated-call limits. Subsequent work adds queued TTL, conservative activity monitoring, and durable delegated fallback settings; see the current compatibility document for their exact scope and verification. `2730bca4e` adds eligible Claude user/project/plugin commands, with explicit evaluator limitations. The baseline rows below are retained as audit history.

**Status key:** Applied = an observed native consumer; Partial = only some fields/paths or semantics are preserved; Not applied = no consumer in the default V2 setup graph (may still work through the legacy server/CLI); CLI/migration = only that path is evidenced. Optional schema fields are unset unless the cited nested schema declares a default.

## Highest-impact gaps

1. **`background_task` is not bridged.** V2 delegation calls the native `subagent` executor and forwards only the native agent/prompt/model/session/background fields (`src/v2/delegation.ts:420-467`). It does not construct the V1 background manager or consume `BackgroundTaskConfig` (`src/config/schema/background-task.ts:3-29`; V1 wiring: `src/create-managers.ts:135`). Thus OMO per-key concurrency, depth/descendant caps, stale/TTL cleanup, max tool calls, circuit breaker, and polling controls are not applied; host-native subagent behavior is a different policy surface.
2. **Runtime error fallback is absent.** `model_fallback` and `runtime_fallback` are consumed by V1 session hooks/events, not `setupV2` (`src/plugin/hooks/create-session-hooks.ts:105-110,218-220`, `src/plugin/event.ts:42-44`). V2's `model-resolution.ts:127-184` chooses an available initial model; that does not retry a request after provider/API failure.
3. **`disabled_providers` is a concrete enforcement gap.** The shared filter sees only configured agent/category `model` and `fallback_models`; it filters/replaces those where possible, but when no allowed fallback exists it only logs/adds a config error and leaves the disabled primary intact (`src/shared/disabled-providers.ts:38-52,55-92,103-123`). It does not filter category `models` chains. V2 then preserves explicit provider/model values verbatim and selects builtin agent fallback/default models without this setting (`src/v2/model-resolution.ts:127-184`); category task resolution checks native availability but not disabled providers (`src/v2/delegation.ts:109-149`). Claude/file-backed custom agent configs are merged directly into the native registry (`src/v2/agents.ts:461-470`) without a disabled-provider check. Any disabled provider still enabled in OpenCode can therefore be selected from these paths. This is a source-level enforcement risk; no runtime reproduction was run for this audit.
4. **The experimental task-system adapter is partial at runtime.** `experimental.task_system` gates registration (`src/shared/task-system-enabled.ts:7-9`, `src/v2/tool-task.ts:65-89`), but runtime validation reproduced `task_create`, `task_get`, and `task_update` being skipped by native host Standard-Schema JSON-schema conversion: legacy Zod 4.1.8 field schemas wrapped by root Zod 4.6.5 fail `~standard.jsonSchema.input({target:"draft-2020-12"})`. This was subsequently fixed in commit `360835f85`. Treat task-system as **not yet runtime-usable as a complete feature** on this baseline, despite source registration; `task_list` failure was not confirmed here.
5. **Goal behavior has partial parity.** `goal.enabled` gates tools/commands/continuation, but V2 does not consume `goal.auto_start`, `goal.default_max_iterations`, or `default_mode.goal` (V2 references: `src/v2/commands.ts:125-127`, `src/v2/tool-goal.ts:29-34`, `src/v2/lifecycle.ts:246-273`; schema defaults: `src/config/schema/goal.ts:3-10`, `src/config/schema/default-mode.ts:3-16`). Auto-create and the configured 100-iteration cap are therefore not applied.
6. **`mcp_env_allowlist` is not installed into the shared Claude MCP loader in V2.** The V1 config handler calls `setAdditionalAllowedMcpEnvVars` (`src/plugin-handlers/config-handler.ts:95-99`); V2 directly calls `loadMcpConfigs` without it (`src/v2/mcp.ts:55-60`). The loader starts with only its builtin allowlist (`packages/claude-code-compat-core/src/features/claude-code-mcp-loader/configure-allowed-env-vars.ts:1-31`) and blocks other expansions (`packages/claude-code-compat-core/src/features/claude-code-mcp-loader/env-expander.ts:12-26`). Result: configured custom variables are not expanded in V2 (restrictive compatibility loss, not evidence of secret exposure).
7. **Team mode is deliberately disabled.** When configured true, `setupV2` logs and passes a clone with `team_mode.enabled:false` to all adapters (`src/v2/setup.ts:27-34`). Native team manager, team tools, team skill, and team prompt behavior are unavailable; hyperplan/team keyword paths report unavailable or do not inject the team prompt (`src/v2/context-hooks.ts:80-85,105-107`; `src/v2/commands.ts:191-193,237-240`).

The [background policy source audit](opencode2-background-policy-audit.md) expands the actual defaults and route-specific behavior of `background_task`; several schema comments differ from the effective V1 constants. Its proposed implementation is not a completed-feature claim.

The [fallback source audit](opencode2-fallback-audit.md) checks both legacy fallback consumers against the official 2.0.18 retry, transport, and session APIs. Primary and compaction retries can have identical public identifying fields; title generation does not use that retry policy. No faithful generic fallback port has been established through those APIs. This is a source-level limitation, not a runtime reproduction or an assertion that all narrower fallback designs are impossible.

### Goal auto-start source clarification

A follow-up audit of upstream 5.0.0 found that `goal.auto_start` is passed as `autoStart` to `createGoalHook`, but that hook does not read it (`src/plugin/hooks/create-session-hooks.ts:168`, `src/hooks/goal/index.ts`). It is therefore an accepted but unused setting in that upstream path, not an established V2 regression. `default_mode.goal` does have a separate chat-message consumer, but its behavior differs from its documentation: `handleGoalMessage` first passes every eligible message to `parseGoalCommand`, whose nonempty default case is `setObjective`. The later first-message/default-mode branch requires `show`, which that parser returns only for empty input; its nonempty-objective condition cannot then succeed (`src/plugin/chat-message/loop-commands.ts:25-65`, `src/hooks/goal/command-arguments.ts:9-28`). The existing positive auto-start test does not test the disabled or subsequent-message cases. This is a source finding, not an OpenCode 1 runtime reproduction. The native adapter continues to require an explicit goal command/tool and does not copy the upstream behavior of replacing a goal from ordinary messages.

## Follow-up order suggested by source evidence

1. Fix task adapter schema conversion and prove all four native tools execute in a host test; this baseline blocker was subsequently fixed and verified in `360835f85`.
2. Decide whether native child-task semantics are an acceptable replacement for each `background_task` limit. If not, implement enforcement at the native `task` boundary (including resumed children) before advertising the config as effective.
3. Thread `disabled_providers` through both built-in agent and default-category fallback selection, then test each fallback chain with a disabled provider.
4. Implement native request-failure fallback or explicitly document `model_fallback`/`runtime_fallback` as unsupported in V2; keep this distinct from startup catalog selection.
5. Add goal auto-start/iteration policy if parity is required; otherwise remove or qualify the accepted config semantics in V2-facing docs.
6. Wire the user-only MCP env allowlist into V2's load path with per-plugin/config isolation, preserving the shared loader's secret checks.
