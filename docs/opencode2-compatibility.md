# OpenCode 2.0.18 compatibility (personal fork from upstream 5.0.0)

This fork is based on the upstream Oh My OpenAgent **5.0.0** release, with local native OpenCode 2 compatibility work at the pinned `@opencode/*` **2.0.18** SDK/schema version. The legacy OpenCode 1.x entry remains separate. The v2 adapter is still incomplete; the table is not a claim of full OMO parity or end-to-end verification for every behavior.

Version checks on 2026-09-27 used the native `@opencode/cli` and `@opencode/plugin` npm packages, whose `latest` tags were both `2.0.18`. The older `opencode-ai` package and GitHub's default latest-release endpoint still pointed to `1.18.32`; those are not the version source for this v2 target. The inspected upstream source is commit `cd9a14a6b688d4021bee381dfd39d2cef9c0f862` (`release: v2.0.18`).

A later same-day registry check found OMO **5.0.1** (`ab725f3299cd5ba8727a999817db8f9d856f2440`) while the OpenCode tags remained **2.0.18**. Its OpenCode conversation-routing change is backported exactly: `writing` now chooses `claude-opus-5-5` at `low`, then `claude-opus-4-6` at `max`, with no Fable 5.1 default rung. Explicit category overrides retain priority. The six affected model-core/OpenCode files match the release, with 28 focused tests and native typecheck passing. The fork retains the 5.0.0 source base; separate Native/Senpi runtime, website and release-metadata updates are outside this OpenCode adapter change.

The native server entry is `packages/omo-opencode/src/v2/server-entry.ts` and exports the OpenCode 2 plugin definition (`id` plus `effect`). It uses the official `fromPromise` adapter for the registries, tools, and hooks assembled by `src/v2/setup.ts`. A scoped boundary restores genuine `Tool.Error` failures from Promise callbacks so native failure handling remains available; unknown defects and interruptions are preserved. The root hybrid export retains legacy `server` and Promise `setup` alongside the native Effect entry. The build stages `server.js`, `tui.js`, shared skill files, and LSP runtime assets under `dist/opencode2/`. The bundles externalize `@opencode/*`, Effect (pinned to the SDK's `4.0.0-rc.112`), OpenTUI, and Solid packages, so this directory is not verified as a relocatable standalone plugin. The installer edits only a user-selected OpenCode config file.

## Native background admission

Commit `1a78d25c5` wraps the host `subagent` executor once and shares that wrapper with `task`, `call_omo_agent`, and `look_at`. It pins the effective model before acquiring a FIFO slot. Exact `modelConcurrency` overrides take precedence over provider overrides, then `defaultConcurrency` (default 5); zero means unlimited. Model variants share a pool. OMO depth (default 3) and active/queued descendant reservations per root (default 24, zero disables) apply to both new and resumed children. OpenCode's independent depth policy remains in force.

The native awaited progress callback binds the child and its restrictions before prompting. Background results retain their slot until terminal execution; foreground settlement can reconcile through the authoritative native idle wait. Resumes use the same child with a new admission generation and require a newer idle marker before an event can release it, preventing delayed prior-generation events from freeing a live slot. OpenCode's projector monotonically advances that marker even when terminal events share a millisecond. Storage is scoped by project, workspace, and canonical directory. Ambiguous crash records, storage failures, and missing pre-prompt progress fail closed instead of admitting extra children. Quotas are serialized within one plugin instance, not atomically across multiple server processes.

Host QA exposed a further adapter bug fixed by `d34962ff5`: the native session API represents an absent stored model variant as `"default"`, which admission initially treated as an unavailable named variant. Inherited parent/child model refs now normalize that sentinel to the base model, matching the host resolver. Explicit user-supplied `#variant` values still undergo the host's strict catalog validation. The regression suite passed five tests with 19 assertions; the failed native resume attempt is retained under `native-runtime-qa/run-2026-09-26T21-00-21-159Z/` in the background-policy evidence directory.

Commit `9b281ad81` additionally reconciles a first-generation new child that completed while the plugin was offline and had no idle marker when bound. Release requires the same child/parent/project/location and a terminal idle timestamp at or after reservation. Resumed or adopted generations still require their existing stricter proof; a later tracked resume retains its own slot. These quotas cover wrapped subagent invocations, not arbitrary later `session.prompt` calls. The restore-edge regression suite passed 22 tests with 76 assertions (`.omo/evidence/20260927-background-admission-null-idle/`); the live reload behavior is separately verified below.

On the integrated `14ebcca634230f0dc8af7ecf71c132b96aec1e09` bundle (`server.js` SHA-256 `db53a8e8ff276bfc1250664348e2c7fbe1f29b6a1026f6d63760fdf7df11c4b3`), the isolated OpenCode 2.0.18 offline-reload run passed **52 distinct named checks / 64 detailed observations**. Its exact model catalog was `omoqa/qa-model` and `omoqa/qa-secondary`, default was `omoqa/qa-model`, active MCP list was empty, and all 32 mock model requests were localhost with zero origin-validation failures. Peak concurrent primary child sessions and peak running admission leases were both 1. During the reload, the config removed OMO while retaining the origin-probe plugin; the same server PID stayed healthy. A held native Explore child succeeded while OMO was absent, but its persisted null-baseline lease remained `running`. Restoring the original plugin order let OMO reconcile that lease to `terminal/succeeded`; the next child then completed under concurrency 1. Both server and mock stopped, and isolated runtime state was retained. Evidence: `.omo/evidence/20260927-native-background-policy/offline-reload-qa/run-2026-09-26T21-59-27-328Z/` (`runtime.json`, `server.log`, and read-only DB observations).

This did not provide seamless parent-session execution during plugin absence: `server.log` records `Failed to drain Session` / `AgentNotFoundError: Agent not found: "sisyphus"`, and read-only DB inspection shows the reload parent's idle outcome was `failed`. The child completed and its lease was reconciled after OMO returned, but the parent failure remains a real unload-side effect.

Commit `14ebcca63` adds `background_task.maxToolCalls` and the repeated-call circuit breaker to owned native children, including foreground and resumed children. The nested `circuitBreaker.maxToolCalls` takes precedence; disabling `circuitBreaker.enabled` disables repetition detection while leaving the hard cap active. The effective defaults are 4,000 total calls and 20 consecutive identical calls. Counters and hashed input signatures persist per session/location; call IDs prevent double-counting. The threshold call is blocked **before** side effects and native interruption is requested. This differs from V1's observation of running tool parts: with a repeat threshold of 5, at most the first four identical calls execute. Parent sessions are excluded. Session deletion clears the policy counters. A tool error is not guaranteed to reach the parent when the child interrupts itself; compact trigger details remain in plugin storage and logs.

Queued reservations now expire after `background_task.taskTtlMs` (default 30 minutes), before any native child is created. Grant, abort, expiry, and disposal share the admission serializer; storage failure retains a fail-closed lease. This TTL does not terminate running children.

Managed running children have a separate activity monitor. A matching fresh execution-start event, session identity, and unchanged idle watermark must establish the current generation before inactivity can interrupt it. `messageStalenessTimeoutMs` applies before first model/tool progress; `staleTimeoutMs` applies afterward, with the shared 30-second minimum runtime. Start/step events alone are not progress. A newer terminal idle marker is reconciled first. Ambiguous or restored runs are treated conservatively; repeated starts cannot authorize interruption of a later unrelated run. The slot stays held until terminal proof, even after an interruption request. The public interrupt API has no reason parameter, so OMO stores the trigger in its own diagnostic record and log.

`sessionGoneTimeoutMs` requires repeated typed missing-session results; a transient error or successful lookup resets that grace. `taskCleanupDelayMs` permits removal of superseded terminal activity metadata during subsequent monitoring/terminal processing; the latest resume-protection state remains. Native sessions are never deleted. `syncPollTimeoutMs` remains unsupported because returning a foreground call early would abandon native result ownership. See [the policy source audit](opencode2-background-policy-audit.md) for the legacy behavior and public API limits.

## Other known gaps

- New delegated children resolve agent/category model chains against the live enabled catalog. Ordered rich fallback entries, fallback-only chains, native variants, and disabled-provider promotion retain their request settings. An explicit category chain cannot silently escape to an unrelated default when exhausted; explicit per-tool model/variant overrides remain strict. Selected settings are persisted before the native pre-prompt progress callback returns and applied only to the matching child's primary context. Resumes retain the stored model/settings rather than rerunning a reordered chain; sibling and auxiliary contexts do not receive this plugin overlay. This is availability selection at delegation time, not provider-error `runtime_fallback`, and initial agent-registry selection remains separate.
- Built-in OMO agents and model/provider selection use the native agent/model registries. Custom agents from user/project Claude agent directories, `agent_definitions`, and prompt-bearing unified `config.agents` entries are merged and registered; built-in IDs remain owned by OMO and host-defined OpenCode agents remain host-owned. `claude_code.agents: false` and `disabled_agents` are applied.
- `disabled_providers` now filters OMO primary, fallback, category, builtin, and file-backed agent model selection. An explicitly blocked agent without an allowed candidate is omitted instead of silently using the host default. A native model-request guard also rejects blocked providers for OMO-owned agents, including auxiliary requests, and resumed OMO children cannot retain a blocked provider. This is OMO selection/execution policy; host-owned agents and the host provider registry are not disabled by this setting.
- Skills are loaded into the native registry and are model-visible by default. Claude `disable-model-invocation: true` and native `metadata.opencode/autoinvoke: false` suppress automatic discovery while leaving explicit invocation available. Because the host can register internal skill transforms after user plugins, OMO also listens for location-scoped `skill.updated` events and appends a policy-only correction if a later transform overrides invocation visibility or re-adds a disabled skill. Native agent prompt factories filter manual-only skills and gate built-in Team skills on `team_mode.enabled`, while preserving non-builtin skills with the same names. Enabled Team/Hyperplan uses adapted native role and delegation instructions. Unit tests cover late overrides, disabled skills, correction-loop prevention, and cleanup; the earlier Team-disabled runtime fixture confirmed `qa-manual-only`, `security-research`, `security-review`, and `team-mode` were absent from every model system prompt, not only the `<available_skills>` block. The later Team-enabled receipt separately verifies full adapted skill delivery. This is event-driven startup reconciliation, not a synchronous guarantee before every first registry read.
- MCP defaults and Claude Code MCP servers are translated to native config. The user-scoped `mcp_env_allowlist` is passed per load, so concurrent native configurations cannot inherit another configuration's mutable legacy additions. Builtin allowed variables remain available; project configuration cannot extend the allowlist. Registry tests cover preservation of native auth/disabled values and explicit `disabled_mcps` removal. The skill MCP adapter keeps original server names for permission compatibility; conflicts and the shared project-scoped lifetime are described in the tool table above.
- OpenCode 2.0.18 does not automatically copy `Agent.Info.request.settings` into the provider request. OMO stores flat `providerOptions` there before mapped top-level fields, then applies the existing `options` object last; its native context hook copies the result to `SessionContext.options`, where the host routes unknown keys through the selected provider. A separate isolated 2.0.18 local-mock fixture with the OMO plugin alone verifies `reasoningEffort` reaches the wire as `reasoning_effort` for built-in Sisyphus and a prompt-bearing custom `api-builder`; top-level temperatures win collisions (`0.31` and `0.42`). OMO options stay out of `request.body`, preserving the host-owned body/header merge path. The focused provider-options fixture passed 12 checks.
- Provider options are preserved in delegated settings and forwarded to native request options, but the host protocol determines which fields reach HTTP. In OpenCode 2.0.18, `packages/ai/src/protocols/openai-chat.ts` lowers reasoning effort and capability-gated storage options; it does not emit `parallel_tool_calls`. A native QA attempt on the repaired `cc82cf38` bundle confirmed the token limits reached the wire while `parallelToolCalls: false` remained in durable child settings without a corresponding HTTP field. This transport limitation is not reported as a successful wire-level option override. Evidence: `.omo/evidence/20260927-opencode2-delegation-fallback/run-2026-09-27T03-28-27.374Z/`.
- The native TUI setup and status sidebar load in the 2.0.18 PTY fixture. The `/omo-status` dialog and blank `/omo-btw` question dialog rendered and were dismissed with Escape. A submitted BTW question then created a distinct native fork, completed a response in that fork, and left the original parent transcript unchanged. OMO uses `/omo-btw` with `/side` as its alias so OpenCode's native `/btw` remains untouched.

- Adaptive-thinking-only Claude models (Opus 4.7+, Fable/Mythos and the Claude 5 generation such as `claude-sonnet-5`, including Bedrock ids like `us.anthropic.claude-sonnet-5-…`) reject an explicit `thinking.type: "enabled"` budget. OMO agents built for these models carry no enabled budget, and a final context hook removes an enabled budget and a custom temperature whenever the model actually requested is adaptive-only (for example Sisyphus registered for Sonnet 4.6 but running on Sonnet 5), so OpenCode core applies adaptive thinking from the model variant. Actual-host QA recorded no thinking/temperature on a `claude-sonnet-5` request and the retained enabled budget on the `claude-sonnet-4-6` control.
- OMO configuration is read from `~/.omo/omo.jsonc` and every project `.omo/omo.jsonc` up the directory tree (top-level keys plus the `"[opencode]"` block; other harness blocks are ignored). The upstream startup migration may add a `_migrations` marker once and keeps a timestamped backup. If a migration is rejected (for example an unknown key in an older file), the files are left unchanged and still load, with unknown keys ignored, instead of disabling OMO.

## Local fork installation

Use the `codex/opencode2-compat` branch as source and choose an explicit project or config directory. The installer writes an absolute plugin-directory entry and sets `default_agent` to `sisyphus` only when it is absent; it backs up an existing config before editing it.

```sh
git clone --branch codex/opencode2-compat https://github.com/Loxia106/oh-my-openagent.git
cd oh-my-openagent
bun install --ignore-scripts --frozen-lockfile
bun run build:opencode2
bun run install:opencode2 -- --project /path/to/project
# or: bun run install:opencode2 -- --config-dir /path/to/opencode-config
```

This workflow targets OpenCode 2.0.18. It is not the upstream npm installer. Do not interpret passing unit/type/build checks as full behavior parity; use the compatibility table and runtime evidence for the exact build under test.

The installer records an absolute path to this checkout's `dist/opencode2/`. Keep the cloned source checkout and its `node_modules` in place so OpenCode can resolve the external SDK/UI packages and the staged file-backed skill/LSP assets. If the checkout moves, rebuild and rerun the installer for the new path; copying `dist/opencode2/` alone is unsupported.


For a restrictive native OpenCode configuration, use the v2 `permissions` array. Its legacy singular `permission` object migrates `task` to `subagent`; with a wildcard deny, that can hide OMO's separate `task` and `look_at` tools even though native `subagent` is allowed. Preserve separate `task` and `subagent` actions when authoring v2 rules. MCP tools are normally exposed through native CodeMode: both `execute` and the specific registered MCP action must be permitted. Do not replace a deliberate deny with a wildcard allow to make tools appear.
