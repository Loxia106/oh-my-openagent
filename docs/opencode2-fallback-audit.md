# OpenCode 2 fallback source audit

**Scope:** source-only comparison of upstream Oh My OpenAgent 5.0.0 and official OpenCode 2.0.18. This records API and call-path evidence; no runtime validation was performed. The fallback files checked in this fork at `665e01ddc0c623f7cd1e8b5c0b92763bbeb901ba` are unchanged from the OMO source pin below.

**Source pins:** [OMO 5.0.0 source, `eb5c55c67877ef58e58a174b4c26d0c3e941eca0`](https://github.com/code-yeongyu/oh-my-openagent/tree/eb5c55c67877ef58e58a174b4c26d0c3e941eca0) and [OpenCode 2.0.18 source, `cd9a14a6b688d4021bee381dfd39d2cef9c0f862`](https://github.com/anomalyco/opencode/tree/cd9a14a6b688d4021bee381dfd39d2cef9c0f862).

Later changes implement live-catalog availability fallback for new delegated children and persist selected rich request settings for resume. Actual disabled-provider promotion also carries entry settings. These changes do not implement provider-error retry or change the startup-catalog boundary described below; see [current compatibility and verification](opencode2-compatibility.md).

## V1 consumers and defaults

`runtime_fallback` is disabled by default. Its defaults are retryable statuses `[429, 500, 502, 503, 504]`, three fallback attempts, a 60-second cooldown, a 30-second timeout, notifications enabled, and no automatic primary-model restoration. A separate 90-second first-progress watchdog applies to silent subagent sessions. The actual consumers are the session error/status and assistant-message error/retry-signal handlers, plus the watchdog; fallback models resolve from configured agent/category chains. Dispatch aborts the active request and replays the prior user payload with the next model through OMO's internal prompt gate. See [`constants.ts`](https://github.com/code-yeongyu/oh-my-openagent/blob/eb5c55c67877ef58e58a174b4c26d0c3e941eca0/packages/omo-opencode/src/hooks/runtime-fallback/constants.ts#L13-L43), [`event-handler.ts`](https://github.com/code-yeongyu/oh-my-openagent/blob/eb5c55c67877ef58e58a174b4c26d0c3e941eca0/packages/omo-opencode/src/hooks/runtime-fallback/event-handler.ts#L191-L310), [`fallback-models.ts`](https://github.com/code-yeongyu/oh-my-openagent/blob/eb5c55c67877ef58e58a174b4c26d0c3e941eca0/packages/omo-opencode/src/hooks/runtime-fallback/fallback-models.ts#L14-L98), and [`auto-retry-dispatch.ts`](https://github.com/code-yeongyu/oh-my-openagent/blob/eb5c55c67877ef58e58a174b4c26d0c3e941eca0/packages/omo-opencode/src/hooks/runtime-fallback/auto-retry-dispatch.ts#L89-L161).

`model_fallback` is also disabled by default and is only instantiated when enabled and its hook is enabled. Its event path is disabled while `runtime_fallback` is active. On retryable assistant/session errors or retry-status events, it arms a configured or agent-default chain; the `chat.message` consumer changes the **next outgoing message's** model and variant. For eligible foreground/synchronous-child sessions it may abort and enqueue a `continue` prompt through the same internal gate. It does not directly persist a session model switch. `experimental.model_fallback_title` is a separate opt-in. See [`create-session-hooks.ts`](https://github.com/code-yeongyu/oh-my-openagent/blob/eb5c55c67877ef58e58a174b4c26d0c3e941eca0/packages/omo-opencode/src/plugin/hooks/create-session-hooks.ts#L105-L129), [`event-model-fallback.ts`](https://github.com/code-yeongyu/oh-my-openagent/blob/eb5c55c67877ef58e58a174b4c26d0c3e941eca0/packages/omo-opencode/src/plugin/event-model-fallback.ts#L107-L235), and [`chat-message-fallback-handler.ts`](https://github.com/code-yeongyu/oh-my-openagent/blob/eb5c55c67877ef58e58a174b4c26d0c3e941eca0/packages/omo-opencode/src/hooks/model-fallback/chat-message-fallback-handler.ts#L23-L35).

## Native API boundary

The public [`SessionRetry`](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/plugin/src/promise/session.ts#L127-L150) has session, agent, model, structured error, attempt, and a mutable `{ retry, delay }` decision. It has neither request kind nor request ID. OpenCode invokes the same retry policy for primary model attempts and for compaction's `transient()` retries: the primary runner passes its selected session agent/model at [`runner/llm.ts`](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/runner/llm.ts#L235-L263); compaction passes its current context agent/model at [`compaction.ts`](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/compaction.ts#L546-L556) and [again for its second summary request](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/compaction.ts#L632-L638). The identifying fields can therefore be identical. A retry hook cannot safely infer “primary” from session, agent, model, or attempt alone.

Title generation can overlap the primary run, but it is not this ambiguity: [`title.ts`](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/title.ts#L66-L97) catches provider errors and returns no title rather than calling the retry policy. The native retry schedule is capped at ten retries, with exponential delays and a bounded provider `Retry-After` ([`retry.ts`](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/runner/retry.ts#L67-L119)); that is distinct from V1's three fallback-model attempts and 30-second escalation timeout.

Native `http.response` carries `kind` (`primary`, `compaction`, `title`, or `generate`), so a handler can identify returned HTTP statuses. It runs only after the HTTP handler returns; a thrown connect/read failure bypasses that response hook ([`session.ts`](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/plugin/src/promise/session.ts#L57-L87), [`model-request.ts`](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/model-request.ts#L295-L323)). Experimental WebSocket hooks also carry `kind`, but expose handshake/send/receive rather than a failure callback ([`session.ts`](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/plugin/src/promise/session.ts#L89-L125)). Thus a response-status-only fallback is a possible narrower behavior, not a general substitute for V1 error and timeout handling.

The host exposes [`session.step.failed`](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/schema/src/session-event.ts#L375-L390) and a distinct [`session.compaction.failed`](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/schema/src/session-event.ts#L626-L638) event. `session.step.failed` is not an exhaustion signal: the step runner may publish it for a failed stream and then return `Outcome.Continue` to retry that same step when output had started ([`step.ts`](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/runner/step.ts#L218-L254)). A retry before output starts follows `Outcome.Retry` earlier and does not publish that failure event there ([`step.ts`](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/runner/step.ts#L174-L190)). Thus the event identifies a failed primary step but does not by itself prove the primary execution is exhausted. A follow-up fallback would not replace the failed active request: public `session.switchModel` publishes a persistent model-selection event ([`session.ts`](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/session.ts#L97-L108)), while public `session.prompt` admits a new text/files/agents/skills input and has no per-prompt model override ([`prompt-input.ts`](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/schema/src/prompt-input.ts#L29-L35), [`session.ts`](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/session.ts#L146-L176)). Reusing an existing prompt ID reconciles with its existing admission; a new ID queues another input. For a foreground native subagent, the parent tool blocks on the child job and returns a tool failure once that job reports error, with the child session ID for follow-up ([`subagent.ts`](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/tool/plugin/subagent.ts#L220-L256)). A later prompt may create a successor child execution, but it does not turn the already-returned parent tool result into success.

## Assessment

No faithful generic V1 port is established using the current public 2.0.18 APIs. The safe boundary is to leave model switching out of the untyped-by-kind retry callback; retry-delay policy based on the structured error is separable. A narrowly scoped HTTP-primary-status behavior could be evaluated independently, with its transport/WebSocket coverage and persistent `switchModel` semantics made explicit.

For closer parity, the host would need to expose request kind and unambiguous attempt correlation on retry, plus a model override scoped to the current primary retry rather than a durable session selection. Preserving V1's timeout/watchdog abort-and-replay behavior also needs a supported way to replace or transfer the active admission while retaining the original input and foreground child-job result. These are host API improvements to consider, not claims that every possible fallback design is impossible.

## Agent startup `fallback_models` is separate from runtime error fallback

This source-only comparison pins the V1 files to OMO commit [`eb5c55c67877ef58e58a174b4c26d0c3e941eca0`](https://github.com/code-yeongyu/oh-my-openagent/tree/eb5c55c67877ef58e58a174b4c26d0c3e941eca0) and the V2 port to fork commit [`14ebcca634230f0dc8af7ecf71c132b96aec1e09`](https://github.com/Loxia106/oh-my-openagent/tree/14ebcca634230f0dc8af7ecf71c132b96aec1e09). No runtime test was performed for this section.

V1 built-in agent startup does not consume `agents.<name>.fallback_models`: its resolver accepts the UI-selected model, `override.model`, and built-in requirement chain, and the general-agent registration preserves an unresolved explicit model or uses the first built-in fallback. It does not pass the user fallback list into that decision ([`model-resolution.ts`](https://github.com/code-yeongyu/oh-my-openagent/blob/eb5c55c67877ef58e58a174b4c26d0c3e941eca0/packages/omo-opencode/src/agents/builtin-agents/model-resolution.ts#L4-L16), [`general-agents.ts`](https://github.com/code-yeongyu/oh-my-openagent/blob/eb5c55c67877ef58e58a174b4c26d0c3e941eca0/packages/omo-opencode/src/agents/builtin-agents/general-agents.ts#L62-L96)). Thus V2's startup chain behavior below is a limitation of the current port, but not a missing V1 built-in-startup behavior.

The V1 delegated-task path is different. It passes normalized agent or category fallbacks to the delegate resolver. With a nonempty available-model catalog, a reachable explicit primary wins; if it is absent, the resolver promotes the first reachable configured fallback and otherwise preserves the explicit primary. Without an explicit primary, it tries the matched category/agent model first (an explicitly configured category model can bypass catalog validation), then configured fallbacks, then the built-in requirement chain ([`subagent-model-resolution.ts`](https://github.com/code-yeongyu/oh-my-openagent/blob/eb5c55c67877ef58e58a174b4c26d0c3e941eca0/packages/omo-opencode/src/tools/delegate-task/subagent-model-resolution.ts#L31-L60), [`model-selection.ts`](https://github.com/code-yeongyu/oh-my-openagent/blob/eb5c55c67877ef58e58a174b4c26d0c3e941eca0/packages/delegate-core/src/model-selection.ts#L82-L125), [fallback ordering](https://github.com/code-yeongyu/oh-my-openagent/blob/eb5c55c67877ef58e58a174b4c26d0c3e941eca0/packages/delegate-core/src/model-selection.ts#L139-L205)). That is delegated-task behavior, not evidence that V1 initial built-in registration used the same chain.

The V2 registry parses the ordered per-agent chain, but current initial resolution has a catalog-availability gap. If an explicit model's provider is allowed, `resolveExplicitModel()` returns that configured qualified value even when the model is absent or disabled in the catalog; it only considers the fallback list when the primary provider is disabled. In that special path it returns the first provider-allowed fallback without verifying that the fallback model itself is enabled and present. With no explicit primary, a category is considered first and primary agents then try the host default and built-in requirement chain; a per-agent fallback-only list is not considered ([`agents.ts`](https://github.com/Loxia106/oh-my-openagent/blob/14ebcca634230f0dc8af7ecf71c132b96aec1e09/packages/omo-opencode/src/v2/agents.ts#L250-L260), [`model-resolution.ts`](https://github.com/Loxia106/oh-my-openagent/blob/14ebcca634230f0dc8af7ecf71c132b96aec1e09/packages/omo-opencode/src/v2/model-resolution.ts#L170-L204), [no-primary ordering](https://github.com/Loxia106/oh-my-openagent/blob/14ebcca634230f0dc8af7ecf71c132b96aec1e09/packages/omo-opencode/src/v2/model-resolution.ts#L207-L278)). The separate V2 category resolver already selects only enabled, non-disabled catalog models from its ordered category chain ([`delegation.ts`](https://github.com/Loxia106/oh-my-openagent/blob/14ebcca634230f0dc8af7ecf71c132b96aec1e09/packages/omo-opencode/src/v2/delegation.ts#L111-L143)).

Validated config also passes through `applyDisabledProviders()`: it filters fallback entries whose providers are denied and replaces a denied primary with the first provider-allowed entry, without checking catalog availability. Thus the provider-disabled path can still hand an unavailable fallback to the agent registry ([`validate.ts`](https://github.com/Loxia106/oh-my-openagent/blob/14ebcca634230f0dc8af7ecf71c132b96aec1e09/packages/omo-opencode/src/config/validate.ts#L181-L205), [`disabled-providers.ts`](https://github.com/Loxia106/oh-my-openagent/blob/14ebcca634230f0dc8af7ecf71c132b96aec1e09/packages/omo-opencode/src/shared/disabled-providers.ts#L55-L92)).

Fallback selection must wait for an authoritative catalog. The V2 catalog starts empty and records synchronous transform snapshots; those snapshots do not identify whether host composition is complete. After setup, the registry queries the public composed model/default/provider APIs on a detached task and reloads agents if the snapshot changes ([`model-resolution.ts`](https://github.com/Loxia106/oh-my-openagent/blob/14ebcca634230f0dc8af7ecf71c132b96aec1e09/packages/omo-opencode/src/v2/model-resolution.ts#L20-L59), [`registry.ts`](https://github.com/Loxia106/oh-my-openagent/blob/14ebcca634230f0dc8af7ecf71c132b96aec1e09/packages/omo-opencode/src/v2/registry.ts#L69-L97), [setup ordering](https://github.com/Loxia106/oh-my-openagent/blob/14ebcca634230f0dc8af7ecf71c132b96aec1e09/packages/omo-opencode/src/v2/registry.ts#L99-L143)). The current snapshot has no readiness marker. The resolver deliberately preserves an explicit qualified model when the early catalog does not contain it ([test](https://github.com/Loxia106/oh-my-openagent/blob/14ebcca634230f0dc8af7ecf71c132b96aec1e09/packages/omo-opencode/src/v2/model-resolution.test.ts#L28-L39)); any catalog-aware fallback change must retain that behavior until the composed catalog has been captured.

There is also a settings loss when a fallback entry is promoted: the V2 chain parser retains only `model` and `variant`, while fallback objects may specify reasoning, temperature, `top_p`, token limits, and thinking. V1's delegate path applies the selected entry's settings to the resulting model configuration ([V2 parser](https://github.com/Loxia106/oh-my-openagent/blob/14ebcca634230f0dc8af7ecf71c132b96aec1e09/packages/omo-opencode/src/v2/agents.ts#L233-L247), [fallback schema](https://github.com/code-yeongyu/oh-my-openagent/blob/eb5c55c67877ef58e58a174b4c26d0c3e941eca0/packages/omo-opencode/src/config/schema/fallback-models.ts#L4-L20), [V1 settings application](https://github.com/code-yeongyu/oh-my-openagent/blob/eb5c55c67877ef58e58a174b4c26d0c3e941eca0/packages/omo-opencode/src/tools/delegate-task/fallback-entry-settings.ts#L4-L22)). Catalog-aware initial agent fallback selection and fallback-entry settings propagation are not implemented or runtime-verified by this audit.
