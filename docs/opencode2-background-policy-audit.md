# Native V2 background-task policy audit

**Scope:** read-only comparison at OMO `de667dd0e41cfa07be58da072606aa68068f8904` and official OpenCode `2.0.18` source `cd9a14a6b688d4021bee381dfd39d2cef9c0f862`. This is a recorded baseline source audit. It does not claim that the proposed policy implementation is present; consult the current compatibility matrix for accepted changes.

The baseline gaps below predate the implemented admission quotas, tool-call limits, queue TTL, and generation-scoped activity monitor. The [current compatibility document](opencode2-compatibility.md#native-background-admission) records the supported policies and retained boundaries, including host-owned session deletion and unsupported foreground polling timeouts.

## Finding

`BackgroundTaskConfigSchema` is still part of OMO's validated config, but a targeted search of `packages/omo-opencode/src/v2` found no references to `background_task` or any of its fields. The current V2 path therefore does not apply this policy.

V2 does have a suitable public control surface: the native `subagent` tool, `ctx.tool.transform` and `tool.hook("execute.before"/"execute.after")`, `ctx.session.get/wait/interrupt`, `ctx.event.subscribe`, and durable `ctx.storage`. The native host already creates and prompts child sessions, handles background jobs, enforces its own depth/permission rules, and emits terminal execution events. OMO should wrap that executor once and route aliases through the same wrapper; it should not make a second session-creation implementation.

Today `registerV2Delegation` captures `subagent`, adds OMO aliases, and records the child ID when the alias forwards `ToolContext.progress` (delegation.ts:420-467). It leaves native `subagent` registered when `task` is enabled (delegation.ts:711-716; it removes it only when `task` is disabled). Thus direct native calls do not pass through the alias's launch recorder. The current event loop's `markStarted/markTerminal` does nothing for IDs without a stored run (delegation.ts:718-741; task-state.ts:214-224). This is the primary bypass to close before claiming policy coverage.

## V1 field behavior and V2 comparison

The schema is `packages/omo-opencode/src/config/schema/background-task.ts:3-31`. Effective behavior below comes from consumers/constants, not the schema comments alone.

### V1 scope caveat

These policies were not uniform across every V1 “subagent” route either. Background/unstable flows using `BackgroundManager.launch` are queued and tracked. The synchronous `delegate_task` path separately acquires model concurrency and reserves depth/descendants, but its sync runner does not register a BackgroundTask progress record (sync-task.ts:28-49, 97-114). Synchronous `call_omo_agent` reserves depth for a new session but uses its own fixed 5-minute completion poller; resuming an existing `session_id` bypasses new-spawn reservation (call-omo-agent/tools.ts:186-220; sync-executor.ts:88-102, 181-185). Do not describe circuit/stale/TTL as universal V1 guarantees without porting their boundary intentionally.

V1 manager maps, root descendant counts, `TaskHistory`, and the task registry are process-memory/globalThis state: manager.ts:247-309, task-history.ts:19-60, task-registry.ts:3-29. OpenCode sessions themselves are host-persisted. V2 already uses durable `ctx.storage` run records and parent-child indexes (task-state.ts:80-99, 122-199); they currently store parent, start time, status, and blocked actions, not model, concurrency lease, tool count, circuit window, or activity timestamp.

## Native V2 API evidence

- `Plugin.Context` exposes `tool`, `session`, `event`, and `storage`, but no raw `client` (plugin/promise/plugin.ts:25-53).
- Tool hooks provide `execute.before/after` with effective tool name, session ID, message ID, and tool call ID (plugin/promise/tool.ts:38-63). Tool transform supports getting/updating/removing native tool definitions (plugin/promise/tool.ts:16-35).
- Session domain exposes `create/get/switchAgent/switchModel/prompt/interrupt/wait` and context/hooks; it does not expose `delete` or session listing (plugin/promise/session.ts:153-170).
- Native `subagent` accepts agent, model, optional existing `sessionID`, and `background`; it checks agent permission, validates that resumed sessions are direct children, selects model as override → agent → parent, and creates/prompt child session (core/tool/plugin/subagent.ts:29-48, 138-193).
- Foreground native calls block on the child job; background calls return a session ID and register a completion notifier (core/tool/plugin/subagent.ts:200-255; core/session/subagent-job.ts:23-58).
- `ctx.session.wait` waits until execution is idle; core terminal events are `session.execution.started/succeeded/failed/interrupted` (core/session/session.ts:266-269; core/session/execution.ts:114-149). These are the preferred lifecycle source over polling messages.
- Plugin storage provides `get/set/remove/scan`, but no compare-and-swap or transaction (plugin/promise/storage.d.ts:3-8). A per-plugin-instance lock can serialize admission; strict quota guarantees across multiple concurrent server/plugin instances would need a shared atomic primitive not present in this API.

## Minimal implementation and verification plan

1. **One admission/release wrapper:** Wrap the effective native `subagent.execute` in the shared tool transform, and have OMO `task` / `call_omo_agent` call the same wrapper. Preserve the original schema, permission check, progress, output, foreground/background behavior, and abort signal. This is necessary so native-direct calls cannot bypass configured caps.
2. **Preflight and reservation:** For a new child, resolve the current session ancestry with `ctx.session.get` and fail closed on a cycle/unreadable parent; resolve exact model using host order (explicit model → configured agent model → parent model); acquire FIFO concurrency and reserve root live-descendant capacity before invoking host create. Treat concurrency 0 and descendant cap 0 according to their distinct V1 semantics. Roll back both on any failure before a child session ID is committed.
3. **Persisted run lifecycle:** Interpose native `progress({sessionID})` to persist child ID, parent/root, model, started time, count/window and lease key before the host prompts it. Keep lease for background children until a terminal execution event; release once on success/failure/interruption/deletion. A resumed child is the same descendant, but reacquires concurrency and retains tool counters/window. Reject or explicitly define concurrent resume of an already-running child.
4. **Tool-loop safety:** Count a tool call once by child session + native call ID. Apply the hard tool-call cap regardless of repeated-call detector toggle; update stable tool/input signature; interrupt on the configured limit. Keep call IDs/session attribution scoped so a parent’s delegation call is not charged to the child.
5. **Timeouts and cleanup:** Use persisted activity time plus native execution events for stale policy. If adding a timeout around `ctx.session.wait`, specify whether expiry leaves the child running or calls `ctx.session.interrupt`. Prune OMO metadata after cleanup delay but retain host-owned sessions; session deletion is not exposed by this SDK. On plugin cleanup, abort event subscription, dispose hooks/transforms, and release only in-memory waiters; do not mark a still-running host child complete.
6. **Unit tests:** Cover precedence/key pooling and zero semantics; simultaneous acquire/rollback; depth boundaries/cycle/get failure; descendant reservation/zero/resume/restart; direct native and both aliases; once-per-call counters, nested max override, disabled repeated detection with hard cap still on; running vs stale/missing/unknown session, interruption and terminal cleanup; timeout signal vs child interrupt; cleanup/dispose and double-release.
7. **Local mock-host acceptance:** Against official 2.0.18 with a local fake provider and isolated DB/config, start children through native `subagent`, `task`, and `call_omo_agent`. Assert the model/provider cap bounds overlapping requests; depth/live limits block at boundary (including parallel sibling launches); resumed runs keep counters and do not double-charge descendants; background output wait and cancellation settle the same session; scripted repeated tool calls trip the breaker; deleted/stale sessions release reservations; plugin reload reconstructs active leases from storage and does not admit a cap-violating sibling. Use low permitted test limits (concurrency 1, descendants 1, maxToolCalls 10, consecutiveThreshold 5); exercise minute-scale stale timeouts in fake-clock tests and test at least one real terminal/deleted event without waiting on a paid provider.

## Chosen compatibility boundaries

The native adapter will retain OpenCode's independent depth policy, so effective depth is the stricter of OMO and host limits; it will not silently raise the host setting. Cleanup will prune plugin metadata without deleting native sessions. Admission quotas will be serialized within one plugin instance, with conservative restart reconciliation; storage has no atomic primitive for a strict multi-process quota. A synchronous wait timeout must report a still-running child accurately; the mechanics of detaching without cancelling the native job still require implementation and verification. Admission will cover the native executor and both OMO aliases consistently, which is stronger than some legacy synchronous paths.

These are implementation decisions, not completed-feature claims. In particular, `Session.Info.outcome` and `time.idle` describe the last completed execution and do not prove the current run is idle. A resumed run must retain a baseline or generation marker so stale terminal information cannot release a live reservation.
